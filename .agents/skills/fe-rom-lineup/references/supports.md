# 支援与队伍协同

完整名单必须检查支援；支援是两名单位及其共同使用方式的收益，不能作为单人的固定成长分。它可以影响同定位替换、搭档分配与出击组合，重要性由任务、已实现收益和培养条件决定，不固定“永远最后考虑”或“有支援就优先”。

## 1. 先取配对，不改候选池

```bash
node src/index.ts supports <db>
node src/index.ts availability <db> --full
```

`supports.data` 每行是 `a < b` 的单位 ID 配对，含：

- `aToB`：单位 a 的支援记录指向 b，形状为 `{ initial, growth }`；
- `bToA`：反方向记录；缺失方向为 null，不拿另一方向补齐；
- `reciprocal`：两个方向都存在，不保证数值相同、能达成支援或已完成对话。

`initial` 是 ROM 的初始点数，`growth` 是表里的成长字节；它们不是当前存档进度、等级或战斗加成。双方不一致时保留原值，不平均，也不只挑更有利的一边。

按先前固定的候选 ID 集合过滤配对。先看两人都在名单内的边，再看同定位替代者与已有核心之间的边；不要因支援表出现名字就把 unresolved、序外或无入队证据者加入主线。

## 2. 共同出勤不是共同站位

限定同一路线，用 `availability --from-position <当前位置> --before-position <目标进场位置> --full`，求两人 `available` / `forced` 位置的交集。交集章数是共同出勤机会指标，不是支援培养回合数，也不证明同时部署。目标章状态另查；不把该章自身回合用于证明入场已练成支援。模型播放序含互斥分支时不能跨分支合算。

还要检查：

- 单章部署位与强制出击，能否真的让两人同行；
- 支援成长所需的邻接、距离、战斗、对话或其他条件，这个 hack 是否沿用原版；
- 起始/当前点数、等级门槛、章节上限或冷却、对话是否已完成；
- 是否愿意付出额外回合、站位或移动自由度，以及搭档路线是否兼容。

没有存档时不称“已有 A 支援”；共同窗口长、growth 大也不保证能练成。一个飞行单位与步兵有配对，不自动说明双方能在关键行动时保持支援距离。

## 3. 加成从本 ROM 查询

```sql
SELECT u.id, u.name, u.affinity_id, a.name AS affinity_name,
       b.atk_half, b.def_half, b.hit_half,
       b.avoid_half, b.crit_half, b.crit_avoid_half
FROM units u
LEFT JOIN affinities a ON a.id = u.affinity_id
LEFT JOIN support_bonuses b ON b.affinity_id = u.affinity_id
ORDER BY u.id;
```

查询只补充相同候选 ID 的事实。缺失加成保持未知；不把攻击、命中、回避等全部当成同一“战力点”。加成改变某个命中或生存判断时，说明具体情景与依据。

`*_half` 是尚未除二的原始半点值，不是最终属性。`src/tables/supportBonus.ts` 记录了一套已检查的 FE8 规则，但不能保证所有 hack 都沿用其门槛、范围、累计或取整方式。只有当前 ROM 的规则和表可解释时，才按声明的已达等级或目标等级情景计算。若采用该 FE8 规则，双方 affinity 与方向等级都参与，最后对所有有效搭档累计后除二取整，不能每对先取整再相加。

检查 `supports.meta.diagnostics` 保留的提取诊断：重复 affinity、异常表尾、未知扩展 ID 或缺表都会削弱数值解释。例如 The Drowned King 的 support-bonus 表重复 affinity；写入保留首条不能证明该表可用于战斗计算。空诊断也不认证规则或表完整性；没有取得该层质量证据时注明“加成表完整性未核实”。

## 4. 支援等级是共享约束

先确认本 ROM 是否限制每人的总支援等级、伙伴数量、每对最高等级及互斥关系。不能直接把原版的固定额度套到 hack，也不能为所有候选配对同时分配 A。

若按某种目标等级情景估值，建立具体配对账本：两端单位、各方向目标等级、预计起效时点、所占个人额度、培养与站位条件。一次分配同时占用两端相应资源；同一单位给多个伙伴的承诺必须能共存。当前规则或额度未知时，给互斥备选情景，不宣称整张支援网可同时实现。

## 5. 让支援真正影响取舍

先保留基础能力、个体培养和资源方案，再比较同定位替换或成组替换：

1. 替换后增加/失去哪几条与已选核心的配对；
2. 哪些收益已经实现，哪些有足够条件支持，哪些只是潜力；
3. 支援能否在需要的章节和站位生效，是否值得额外培养、部署和移动代价；
4. 是否改变原人选，或只是给既定名单增加搭档安排。

不要求支援必须改变结论，也不因缺少可量化规则而报告“收益为 0”。保留个人分数与队伍支援情景两层证据；只有用户明确给了合成目标且收益单位可比较时，才声明权重合成。

输出关键配对及替代者，报告等级/时点/额度/站位条件和选择前后差异。局部职业比较不依赖具体角色时，无须拉取整个支援网。
