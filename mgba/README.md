# mgba/ — 凹点助手（mGBA Lua 脚本）

选中一个角色时，实时算出「**从当前随机数状态出发，再消耗 k 个随机数之后升级，
会得到哪些属性成长**」，并标出让收益最大的 k。

**这是一个只读面板**：没有热键，不读键、不改内存、不往游戏里发按键。想换评分焦点、
窗口起点、或锁定某个槽位，改脚本顶部的 `CONFIG` 再重新载入脚本即可。

**选中敌人看到攻击预览时**（`gBattleStats` 低位 = 2），还会多出一块战斗预测：

- 这一仗**会烧掉几个随机数**（逐次出手列出，含未命中/必杀）
- **当前状态下打这个敌人，升级能涨多少点** ← 这是「凹点该怎么凹」的直接答案
- 如果先烧 k 个随机数再打，收益会变成多少（整张表）

```
mgba/
  fe-aodian.lua        主脚本（mGBA Lua，纯 ASCII 面板，只读）
  units.lua            角色 id -> 名字（生成物，由 scripts/emit-mgba-units.ts 产出）
  test/
    selftest.lua       124 项自测：算法 + 假内存端到端（含防闪烁）
    battle_golden.py   独立 Python 实现，产出战斗模型的黄金数值
    run.mjs            用 fengari（Lua 5.3）跑 selftest.lua
```

---

## 1. 怎么用

1. mGBA 载入 ROM（本仓库用 `fixtures/dream-of-five.gba`）。
2. **Tools -> Scripting**（工具 -> 脚本）-> **Open** -> 选 `mgba/fe-aodian.lua`。
3. 脚本窗口出现一块 `FE AODIAN` 文本面板。**只在内容真的变了才重画**，所以静止时
   画面完全不动（不会闪）；每 4 帧检查一次有没有变化。
4. 图上选中角色（或让该角色行动），面板自动切到那个角色。

### 面板怎么读

```
unit   Rena           Lv5   unpromoted [auto]
growth HP70 STR40 SKL55 SPD65 LCK50 DEF30 RES20   <- 角色成长率（含道具加成）
caps   HP60 STR20 SKL20 SPD20 LCK30 DEF20 RES20   <- 实际生效的上限
rng    1234 5678 9ABC   burned since level-up: 0  <- 随机数状态 + 自上次升级以来烧了几个
focus: TOTAL   battle cost: 0                     <- 评分焦点 / 战斗消耗

-- gains if the level-up roll starts after k more RNs (window 0..15) --
     k    HP  STR  SKL  SPD  LCK  DEF  RES   TOT
 *   1    +1    .   +1   +1    .   +1    .     4      <- * = 窗口内并列最优
     2    +1   +1    .   +1    .    .    .     3
...
best   k=1      TOT 4   HP+1 SKL+1 SPD+1 DEF+1
read-only panel: no hotkeys. tune CONFIG at the top of the .lua and reload.
```

`k` = 从**当前**随机数状态再消耗多少个随机数，升级抽点才开始。
`TOT` = 七项成长点数之和。`*` 标出当前评分最高（并列全标）。

### 选中敌人（攻击预览）时

多出一块战斗预测，表的含义也跟着变：

```
vs A  Rena          Lv5  HP 24/24  hit  87 crit   4 AS  12 dmg 11
   T  Wren          Lv3  HP 30/30  hit  52 crit   0 AS  10 dmg  5
cost   6 RNs  (A3 T3)                       <- 这一仗烧 6 个：攻方一次 3 个、守方一次 3 个
ans    attack now -> TOT 2   SPD+1 LCK+1    <- * 当前状态下打这个敌人，升级涨这些

-- burn k RNs, then fight, then level up (cost = battle RNs) --
     k cost   HP  STR  SKL  SPD  LCK  DEF  RES   TOT
  >   0     6    .    .    .   +1   +1    .    .     2   <- > = 现在就打
     1     6   +1    .    .    .   +1    .   +1     3
...
 *   13     5   +1   +1   +1   +1   +1    .    .     5   <- 先烧 13 个再打，能涨 5 点
```

- `cost` 列 = **从该行出发再打这一仗**会烧掉几个随机数。它会随 k 变（命中/未命中
  会改变后续掷骰），所以不是常数。
- `> ` = 「现在就打」那一行（k = 0，不做额外消耗直接开打）。
- `* ` = 窗口内收益最高那一行，也就是「先烧这么多随机数，再打这一仗」的最优解。
- `A3` = 攻方这次出手烧 3 个；`T2-` = 守方烧 2 个且未命中；`A4*` = 烧 4 个且打出必杀。

### 没有热键 —— 要改行为就改 CONFIG

面板是**只读**的。早先版本有一套 `L + …` 组合键（标记基准 / 切换单位 / 搜索 / 写入
随机数 …），但它们会和游戏自己的按键冲突（FE8 里 `L` 是切换光标单位），实际用不上，
已经全部删掉。原来靠热键调的几个参数现在都是 `CONFIG` 项：

| `CONFIG` 项     | 默认     | 作用                                                       |
| --------------- | -------- | ---------------------------------------------------------- |
| `WINDOW`        | `16`     | 面板显示多少行预测                                         |
| `FOCUS`         | `0`      | 评分焦点：`0`=总计，`1..7`=HP/力/技/速/防/魔防/幸运        |
| `UNIT_MODE`     | `"auto"` | `"auto"` 跟随 `gActiveUnit`；`"slot"` 固定看某个槽位       |
| `SLOT`          | `1`      | `UNIT_MODE == "slot"` 时看第几个槽位（1..62）              |
| `K0`            | `0`      | 预测表窗口起点                                             |
| `BATTLE_NUDGE`  | `0`      | 战斗消耗的手动修正（模型在特殊职业/武器上可能差 1-2 个）   |
| `BATTLE`        | `true`   | 是否在预测里计入「打这一仗」消耗的随机数                   |
| `BATTLE_FILTER` | `true`   | 只认「攻方 = `gActiveUnit`」的战斗（过滤敌回合 AI 的模拟） |
| `RENDER_EVERY`  | `4`      | 每多少帧检查一次面板（内容没变就不重画）                   |
| `RENDER_DIFF`   | `true`   | 只在内容变化时才写缓冲（防闪烁）                           |

改完**重新载入脚本**（Tools → Scripting → Open 再选一次本文件）才生效。

### 面板为什么不会闪

mGBA 每往文本缓冲写一次（`clear` / `print`），就会把整块文本纹理重传一遍。
早先的实现是「每 4 帧无条件 `clear` + 重画同一份内容」→ **15 Hz 的纹理重传 →
面板看起来一直在闪**。现在改成：

- **内容不变就一个字节都不碰缓冲** —— 静止时画面完全静止，零重传。
  开关是 `CONFIG.RENDER_DIFF`（默认 `true`；改成 `false` 会退回旧行为，只用来对照）。
- **同一个异常只上报一次** —— 否则某一帧开始每帧抛同一个错时，
  `console:error` 会把 Scripting 控制台每帧刷一次，看着也像在闪。
  （判据是「错误消息变了才再报」，不是「恢复正常就复位」—— 后者会被那些
  「成功但没渲染」的帧清掉状态，照样刷屏。）

> 如果玩的时候随机数一直在变（面板内容真的在变），面板就会跟着更新 —— 那是正常的，
> 不是闪烁。想更安静可以把 `CONFIG.RENDER_EVERY` 调大（比如 10）。

## 2. 怎么用它凹点

### A. 打敌人凹（最自然的那种）

凹点的常规手法就是「找一个敌人打 -> 长经验 -> 升级」，靠**这一仗本身**消耗的
随机数把状态推到合适的位置。助手直接把这个答案算出来：

1. 选中角色 -> 移动 -> 选 **Attack** -> 把光标移到目标敌人上（**出现攻击预览**）。
2. 面板上 `vs` 那一块会显示双方数值、这一仗的随机数消耗（`cost`），
   以及 **`ans  attack now -> TOT n`** —— 就是「当前状态下打这个敌人，升级能涨多少点」。
3. 不满意就换目标敌人，或者先在别处烧几个随机数再回来。表里 `*` 标出的那一行
   就是「先烧这么多再打」的最优解。

`cost` 是**逐次掷骰**算出来的，不是拍脑袋的常数：攻方先手 -> 守方反击 ->
攻速差 ≥ 4 时快的一方再打一次；每次命中消耗 2 个（命中判定）+ 1 个（必杀判定），
必杀后再多 1 个（瞬杀判定）；未命中就只有 2 个。

### B. 看计数器手动凹

盯着 `burned since level-up` 这个数字：它实时显示游戏从**上一次升级**到现在
消耗了多少个随机数。做一个动作 -> 看数字涨了多少 -> 就知道这个动作烧几个随机数。
把数字凹到目标值，再触发升级。

优点：纯观察，不改内存、不按键。缺点：得先找到几个「烧随机数」的动作并量出成本。

**这也是验证 `cost` 模型的办法**：`cost` 行给的是预测值，打一仗之后看计数器实际涨了
多少，两者应当一致。不一致就把 `CONFIG.BATTLE_NUDGE` 调成差值再重载脚本。

> 为什么不做「直接把随机数写到最优位置」那种写入功能：游戏从「你按下」到「真正开始
> 抽点」之间还会消耗 `m` 个随机数（战斗里的命中/必杀判定等等），`m` 静态推不出来，
> 只能实测标定；而且写入属于改内存，风险和不稳定性都比「看表自己操作」大得多。
> 面板给的是**决策**，操作还是你自己来。

## 3. 依据：这些都是从 ROM 自己的代码里反汇编出来的

不是猜的，也不是照抄别的资料。符号表在
`FEBuilderGBA/FEBuilderGBA/bin/Debug/config/data/asmmap_FE8.txt`，反汇编脚本在
`.workbuddy-ai/skills/febuildergba-rom-extraction/scripts/disasm.py`。

| 东西                             | 地址                        | 说明                                                                                                  |
| -------------------------------- | --------------------------- | ----------------------------------------------------------------------------------------------------- |
| 随机数状态                       | `0x03000000`                | 3 × u16。由 `NextRN` / `LoadRNState` / `StoreRNState` 三处字面量互相印证                              |
| `NextRN`                         | `0x08000B88`                | `n = ((s1<<11) \| (s0>>5)) & 0xFFFF`；`t = ((s2<<1) \| (s1>>15)) & 0xFFFF`；`r = n ^ t`；状态左移一格 |
| `NextRN_100`                     | `0x08000C64`                | `(NextRN() * 100) >> 16` -> 0..99                                                                     |
| `Roll1RN`                        | `0x08000CA0`                | `(t > NextRN_100()) ? 1 : 0`，**恰好消耗 1 个随机数**                                                 |
| `RollGrowth`                     | `0x0802B9A0`                | `g = rate/100`；再 `rate%100 > NextRN_100()` 则 `g+1`（成长 >100 合法）                               |
| `CheckForLevelUp`                | `0x0802BA28`                | 7 项抽点 + **全 0 重抽**；成长率取自角色数据 `+0x1C..0x22`                                            |
| `CheckForLevelUpCaps`            | `0x0802BF24`                | HP 上限 60/120、力技速防魔防取职业 `+0x14..+0x18`、幸运硬编码 30                                      |
| `gActiveUnit`                    | `0x03004E50`                | 指针（`SetActiveUnit` @`0x080186D4` 里写死）                                                          |
| `gUnitArray`                     | `0x0202BE4C`                | 步长 `0x48`。步长由 ROM 自带的指针表 `0x0859A5D0` 实测：相邻差恒为 72                                 |
| `Roll2RN`                        | `0x08000CB8`                | 两次 `NextRN_100` 取平均再比，**恰好消耗 2 个随机数**                                                 |
| `gBattleStats`                   | `0x0203A4D4`                | u16 低位：`1` = 真实战斗（掷骰），`2` = 模拟/预览（**不掷骰**）                                       |
| `gBattleActor` / `gBattleTarget` | `0x0203A4EC` / `0x0203A56C` | 步长 `0x80`。前 `0x48` 字节就是 RAM Unit                                                              |
| 战斗标志位                       | `[0x0203A608]`              | 先解引用一次拿到指针，再读 u32。bit14 = 必中                                                          |
| `GenerateCurrentRoundData`       | `0x0802B3EC`                | 一次「出手」的掷骰顺序（见 §3.17）                                                                    |
| `RollRNIfBattleStarted`          | `0x0802A52C`                | 非模拟态下**无条件**转发给 `Roll1RN` —— 概率为 0 也烧 1 个                                            |
| `BattleCheckDoubling`            | `0x0802AF90`                | `\|攻速差\| >= 4` 才追击                                                                              |
| `BattleCheckBrave`               | `0x0802B094`                | 勇者武器 = 武器属性（`+0x4C`）位 `0x20`                                                               |

### 三条容易搞错的细节

1. **成长值顺序是 HP, 力, 技, 速, 防, 魔防, 幸运**，不是 FE 界面上那个
   HP/力/技/速/幸/防/魔 的顺序。面板显示时按界面顺序重排了（`DISP` 表）。
2. **全 0 重抽最多两轮，每轮先抽 HP**。所以一次升级消耗的随机数 ∈
   `{7} ∪ [8,14] ∪ [15,21]`，具体档位受哪些成长率非 0 影响。
   `mgba/test/selftest.lua` 第 3 节用**独立的 Python 实现**算出的分布做交叉验证。
3. **`0x03000008` 是另一个 RNG**（`gOtherRNState`，`GetOtherRN`），与升级无关，
   别读错地址。

### 战斗掷骰：一次「出手」的顺序

`MakeNextBattleHitRound` -> `GenerateCurrentRoundData`。全 ROM 里消耗战斗随机数的
地方只有 8 处（用调用点扫描穷举出来的），顺序**不能乱**：

| #   | 位置                           | 消耗  | 触发条件                                                                  |
| --- | ------------------------------ | ----- | ------------------------------------------------------------------------- |
| ①   | `RollForSureShot` `0x0802B1F4` | 1     | 职业 `0x4A`/`0x4B`，且武器属性不在 `[0x35,0x37]`；成功则置必中标志        |
| ②   | 命中判定 `0x0802B41E`          | **2** | 必中标志（bit14）未置位时。`Roll2RNIfBattleStarted` **全 ROM 唯一调用点** |
| ③   | —                              | 0     | **未命中就在这里跳到函数尾**：下面的 ④⑤ 都不会执行                        |
| ④   | `0x0802B2E8`                   | 1     | 守方职业 `0x6D`/`0x6E`                                                    |
| ⑤   | `RollForPierce` `0x0802B278`   | 1     | 职业 `0x4A`/`0x4B`                                                        |
| ⑥   | 必杀判定 `0x0802B4B2`          | 1     | 命中后                                                                    |
| ⑦   | 瞬杀判定 `0x0802B38C`          | 1     | 必杀后，且守方职业不是 `0x4F`/`0x66`                                      |
| ⑧   | 武器效果 `0x0802B600`          | 1     | 武器效果 = 4 且 幸运 < 30                                                 |

**两个最容易搞错的点**：

1. `RollRNIfBattleStarted` 在非模拟态下**无条件**调用 `Roll1RN`，而 `Roll1RN` 无条件
   消耗一个 `NextRN_100`。所以「必杀率 0」「瞬杀率 0」**照样烧随机数**。
2. 未命中的分支在 `0x0802B43C` 就跳走了，`RollForPierce` 在它**后面** —— 所以
   **未命中不会掷贯穿判定**。（开发时这里放过反，自测里有专门的断言。）

一次普通出手的消耗是：

```
未命中 -> 2          命中 -> 3          命中且必杀 -> 4
```

轮次：攻方 -> 守方（活着的话）-> `|攻速差| >= 4` 时快的一方再来一次；
勇者武器每次出手打两下；任一方 HP（`+0x13`）归零立即结束。

> 面板读的是 `BattleUnit +0x64`（最终命中率）和 `+0x6A`（最终必杀率）——
> 这两个是 ROM 自己算好的（含武器相性、支援、地形、S 级加成），不用自己推。
> 别去读 `+0x60`/`+0x66`（那是没减回避/必杀回避的原始值）。

### 三处仍然没建模的地方

- **武器效果 = 4 的那次掷骰**：要读道具表才知道哪些武器是效果 4，脚本没读，按 0 处理。
- **④ 的「武器效果 != 1」排除条件**：同样要读道具表。
- **必中/贯穿技能的武器属性排除**（`[0x35,0x37]`）：同上。

影响面很小（都是特定武器 / 特定职业），真遇到了就把 `CONFIG.BATTLE_NUDGE` 调成
差值（±1 个），重载脚本即可。

## 4. 维护

### 重新生成角色名表

```bash
node src/index.ts extract fixtures/dream-of-five.gba --out out/dream-of-five.db
node scripts/emit-mgba-units.ts # -> mgba/units.lua
```

名字读不到时脚本会退化显示 `#<id>`，功能不受影响。

### 跑自测

```bash
node mgba/test/run.mjs            # 124 项
node mgba/test/run.mjs --preview  # 附带把面板渲染结果打出来核对版式
```

本机没有独立 Lua 解释器、mGBA 也不支持命令行载入脚本，所以用
**fengari**（Lua 5.3 的 JS 实现）跑。`run.mjs` 默认从自身位置向上找
`node_modules`，装在别处时用 `MGBA_TEST_WORKSPACE` 指到那个工作区：

```bash
mkdir -p ~/.local/share/fe-aodian && cd ~/.local/share/fe-aodian && npm install fengari
MGBA_TEST_WORKSPACE=~/.local/share/fe-aodian node mgba/test/run.mjs
```

自测里有 10 组：RNG 递推性质 / RollGrowth 边界 / 升级消耗分布（对 Python 黄金值）/
上限夹取 / 假内存端到端渲染 / 升级检测 + 计数器 / 成长加成位 / 边界不崩 /
**战斗模型**（掷骰原语、整场消耗、单次出手的确定种子、面板端到端）/
**防闪烁**（内容不变不重画、同一异常只报一次）。

战斗那部分的期望值来自 `mgba/test/battle_golden.py` —— 一份**独立的 Python 实现**，
按同样的反汇编结论重写了一遍。改模型时两边都要改，只改一边自测就会红：

```bash
python3 mgba/test/battle_golden.py   # 打印黄金数值，抄进 selftest.lua（纯 stdlib）
```

### 换 ROM

地址和结构是 FE8U 的。换 hack 时先确认它没改过 `NextRN` / `CheckForLevelUp` /
`GenerateCurrentRoundData`；换版本（FE7U、FE8J…）需要重新反汇编，**不要直接套用**。

脚本会在随机数状态读到全 0 时给出 `RNG state is all zero` 提示。

## 5. 已知限制

- **战斗消耗是算出来的，不是量出来的**。模型覆盖了普通战斗、追击、勇者武器、
  必中/贯穿职业、瞬杀、以及三个特定职业/武器的分支；但 DoF 这个 hack 相对原版
  FE8U 改了多少、改在哪里，没有实机验证过。**第一次用请先拿 `cost` 的预测值和
  `burned since level-up` 的实测值对一下**，不一致就把 `CONFIG.BATTLE_NUDGE`
  调成差值。
- 只在**攻击预览**（`gBattleStats` 低位 = 2）时预测。真实战斗中随机数已经在烧了，
  预测没有意义，所以那时战斗块不显示。
- 预览取消后战斗块会保留（游戏没清 `gBattleStats`），显示的是你最后看过的那个
  预览；打过一场真仗（低位变 1）之后就会消失。
- `burned since level-up` 的起点是「脚本载入后第一次看到的升级」或「上一次升级」。
  如果你在脚本载入前就攒了很多随机数消耗，这个数字会偏大 —— 它量的是**相对量**，
  看变化比看绝对值有用。
- 面板是**纯 ASCII** 的：mGBA 脚本控制台按等宽字体渲染，中文是双宽字符，
  混进表格里列就对不齐。中文说明都在注释和本文档里。
- 脚本是**只读**的：不读键、不写内存、不注入按键。想让游戏和面板同时响应，
  不需要做任何额外设置。
