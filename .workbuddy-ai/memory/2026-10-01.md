## mGBA 凹点助手（新增 `mgba/`）

**产出**：`mgba/fe-aodian.lua`（主脚本）、`mgba/units.lua`（名字表，生成物）、
`mgba/test/{selftest.lua,run.mjs}`（62 项自测）、`mgba/README.md`，
外加 `cli/scripts/emit-mgba-units.ts`（生成名字表）。AGENTS.md 新增 §3.15。

**做了什么**：选中角色时实时算出「从当前随机数状态出发，再消耗 k 个随机数后升级会得到哪些
成长」，标出收益最大的 k；可一键把 RNG 状态写到最优位置。

**全部从 ROM 反汇编得来**（细节见 AGENTS.md §3.15 / `mgba/README.md`）。关键几条：

- 随机数状态 = `0x03000000` 起 3 个 u16（`NextRN`/`LoadRNState`/`StoreRNState` 三处字面量互证）。
  `NextRN` @`0x08000B88` 是移位寄存器式；`NextRN_100` = `(NextRN()*100)>>16`；
  `Roll1RN` = `t > rn100()`，**恰好消耗 1 个**。
- `CheckForLevelUp` @`0x0802BA28`：7 项抽点（`RollGrowth` @`0x0802B9A0`，成长 >100 合法）；
  **全 0 会重抽，最多再 2 轮，每轮先抽 HP** → 一次升级消耗随机数 ∈ `{7} ∪ [8,14] ∪ [15,21]`。
- `CheckForLevelUpCaps` @`0x0802BF24`：HP 60/120、职业 `+0x14..+0x18`、**幸运硬编码 30**。
- `gActiveUnit` @`0x03004E50`；`gUnitArray` = `0x0202BE4C`，**步长 0x48** —— 步长是从
  ROM 自带的指针表 `0x0859A5D0` 实测出来的（相邻差恒为 72），不用猜。
- ⚠️ **成长值存储顺序是 HP,力,技,速,防,魔防,幸运**，**不是** FE 界面那个 HP/力/技/速/幸/防/魔。

**踩过的坑（值得复用）**

1. **`disasm.py` 会静默截断。** 它用 capstone 的 `disasm` 迭代器，**遇到一条无法解码的指令
   就停止**且不报错。反汇编 `0x08000C9C` 附近时输出凭空断了，差点以为 ROM 是空的。
   已给脚本加 `md.skipdata = True`。
2. **校准只能用「随机数状态」匹配，不能用「成长值」匹配。** 第一版用成长值找第一个匹配的 k，
   几千个候选里大量撞车 → 报出 `m = -716`。改成「状态对状态」（48 位）+ 允许抽点后有
   ≤32 步的尾巴 → 唯一解。**这是本次最有价值的一条教训。**
3. **校准要用「升级前」的能力快照做上限夹取** —— 用升级后的 unit 会算错。
4. **批量扫 k 必须增量推进状态。** 第一版每个 k 都 `rnAdvance(state,k)`，是 O(K²)；
   `SEARCH_MAX=4096` 要跑 840 万次递推，会卡住 mGBA 几秒。改成「状态往前推 1 步」。
   自测里加了耗时守卫（<2s）防退化。
5. **mGBA 0.10.5 没有 `gui` 绘图 API**（那是 0.11+ 的），只有 `console:createBuffer(name)`
   + `setSize(cols, rows)` 文本缓冲；**也没有命令行载入脚本**（只能 GUI Open）。
   控制台按**系统等宽字体**渲染 → **面板必须纯 ASCII**，中文双宽会破坏表格对齐。
6. **本机没有独立 Lua 解释器** → 用 **fengari**（Lua 5.3 的 JS 实现，装在托管 node 工作区
   `/Users/woxqaq/.workbuddy-ai/binaries/node/workspace`）。它能搭**假 GBA 内存 + 假
   `emu`/`callbacks`/`console`**，真的调 `frame` 回调走端到端 —— 比只测纯函数强太多。
   脚本里用 `if emu and callbacks then ... else 纯计算模式 end` 让它脱离 mGBA 也能被加载。
7. **升级消耗的随机数分布别靠心算。** 我先写错了两版期望值（以为重抽至少 8 个、以为会出现 14），
   最后用**独立的 Python 实现**算出黄金分布再逐档对齐。
   ⚠️ 重抽**总是先抽 HP**，所以只有「最后一项（幸运）有成长」时才会出现整轮重抽的 14。

**唯一验证缺口**：mGBA 实机加载一次（GUI、无命令行脚本、无显示）只能人工做。

**从 ROM 自己的 ARM 代码解出的完整抽点算术**（写进了 `AGENTS.md` §3.15）

- RNG 状态 `0x03000000`（3×u16，由 `NextRN`/`LoadRNState`/`StoreRNState` 三处字面量互相印证；
  `0x03000008` 是另一个 RNG，与升级无关）
- `NextRN @0x08000B88`、`NextRN_100 @0x08000C64`、`Roll1RN @0x08000CA0`
- `RollGrowth @0x0802B9A0`：`while rate>100: g++, rate-=100` 再 `if rate > NextRN_100(): g++`
- `CheckForLevelUp @0x0802BA28`：7 项顺序 **HP/力/技/速/防/魔防/幸运**（≠ 界面顺序）；
  **全 0 重抽最多 2 轮、每轮先抽 HP、任一非 0 即停** → 一次升级消耗 `{7} ∪ [8,14] ∪ [15,21]`
- `CheckForLevelUpCaps @0x0802BF24`：HP 60/120（判据 `unit[+0x0B] & 0xC0 == 0x80`）、
  力技速防魔防取职业 `+0x14..0x18`、**幸运硬编码 30**
- 成长加成位 `unit->state(+0x0C) & 0x2000` → 每项 **+5**
- `gActiveUnit @0x03004E50`（反汇编 `SetActiveUnit @0x080186D4`）
- `gUnitArray @0x0202BE4C` 步长 **`0x48`**（ROM 自带指针表 `0x0859A5D0` 实测：相邻差恒 72）

**踩过的坑（都值得记）**

1. **校准必须用「随机数状态」匹配，不能用「成长值」匹配。** 最初用 7 个成长值在
   `appliedK..SEARCH_MAX` 里暴力搜首个匹配 —— 值域只有 0..3，几千个 k 里**大量撞车**，
   认错 k（自测报 `m = -716`）。改成用 48 位随机数状态算 `rnStepsBetween`，
   取「抽点结束到 detState 的尾巴最短」的候选，并列时明确报 `tied candidates`。
2. **必须用「升级前」的能力快照做上限夹取** —— 用升级后的 unit 去预测会算错。
3. **mGBA 0.10.5 没有 `gui` 绘图 API**（官方文档确认），只有 `console:createBuffer` 文本缓冲；
   **没有命令行载入脚本**（只能 GUI：Tools → Scripting → Open）。
   控制台用系统等宽字体 → **面板必须纯 ASCII**，中文双宽会破坏对齐（第一版面板全是中文，返工）。
4. **心算重抽规则会错。** 「力 50% 的消耗只出现在 7/8/14/15/21」是错的 ——
   只有**最后一项**有成长时才会出现整轮重抽的 14（重抽总是先抽 HP，前面命中就提前返回）。
   改用**独立的 Python 实现**产出黄金分布，再在 Lua 里逐档对齐：
   `力50 → {7:1008, 9:496, 16:256, 21:240}`、`幸50 → {7:1024, 14:488, 21:488}`、`真实 → {7:2000}`。
5. `LABEL` 曾按界面顺序写，与内部顺序（防在魔防之前）冲突，面板列错位 ——
   改成 `LABEL` 按内部顺序、用 `DISP = {1,2,3,4,7,5,6}` 控制显示顺序。
6. 并列最优原来只标一行 → 改成 `S.bestS1`/`S.bestS2`，**并列最优全部标 `*`**。

**已知限制（写进 README 与脚本头注释，不是遗漏）**

- **`m`（按下热键 → 真正开始抽点之间消耗的随机数）静态推不出来**，只能实测标定
  （自动：按一次 → 等升级 → 反推；手动：`L+↑/↓`）。战斗场景的 `m` 可能不稳定
  （命中判定次数随回合数变），此时只能回到「看计数器手动凹」。
- **本机无法真正在 mGBA 里跑一遍**（GUI、无命令行脚本载入、无显示）——
  所有验证都走假内存 + 反汇编推断。**这是唯一的验证缺口。**

## 经济规划（`cli/scripts/economy-plan.ts` → `out/dream-of-five.economy-{A,B}.md`）

**需求**：规划游戏内金币怎么花、买什么武器道具，兼顾性价比与人员配置。

### 数据链路（全部新增或修正）

1. **物品 `+26` 是 u16「每次使用单价」，不是 u8。** 总价 = 耐久 × 单价，卖价 = 总价 ÷ 2
   （`ItemForm.cs:309-311`）。普通武器高字节为 0，所以 u8 碰巧对；宝石/钱袋用高字节
   （Diamond `0x4E20`=20000、Sapphire 10000、Ruby 5000、`3,000 Gold` `0x0BB8`、Gold Gem 40000）。
   修正后 `validate` 的 `item.priceRule` 仍全过。
2. **金币指令**：`40050300XXXX000021370000`（入手）/ `...22370000`（失去），金额在 `+4`。
   复合形态 `400A0000<ptr>40050300XXXX000021370000`（20 字节）在**偏移 8** 内嵌金额，
   反汇编只返回一条复合指令 → 新增 `findGoldLiteralsIn(code)` 按 4 字节对齐扫字节。
   **全 ROM 只有 4 条**给钱指令（0x9F87FC +10000、0x9FF3E4 +5000、0x14BEE38 +5000、
   0x14BEE54 +3000）+ **4 个金箱**（C3 4000、C22 7500、两张 @001F 各 5000）。
3. **宝箱/村庄/门/制圧点/商店 = 同一个 12 字节 `CONDTYPE.OBJECT` 记录**，挂章节条件表 slot 2，
   `u32(+0)==0` 终止。新增 `cli/src/tables/mapObjects.ts`（`objects` 命令）+
   `shops.ts` 重构为吃 `ChapterObjects`。金箱不变式（物品 `0x77` ⇔ 金额 > 0）进了 `validate`。
   324 个物件：57 宝箱（4 金箱 21500 + 53 物品箱）、33 村庄、106 门、33 商店、95 制圧/民家。

### 两个致命 bug（事件脚本解析）

  一路读过头（330 条 LOAD + 963 次 walk 中断 + 金币虚高到 17 张图共享一笔）。

- 另外新增 `WalkOptions.innerFailure: 'abort' | 'continue'` —— 本 hack 几乎每个子事件都以
  unknown 收尾，忠实模式会过早停下。

## mgba 面板「一直闪」的修复

**症状**：脚本加载后面板一直在闪。**用户问「是定时触发吗？」—— 是。**

**根因**：`render()` 每 `RENDER_EVERY = 4` 帧就无条件 `buf:clear()` + 把同一份内容重印一遍。
mGBA 每写一次文本缓冲就把整块**文本纹理重传**一遍 → 内容没变也 15 Hz 重传 → 看起来一直在闪。

**修法（两层）**：

1. **`CONFIG.RENDER_DIFF = true`（默认）**：把渲染出的文本拼成一个字符串，与 `lastText`
   比较，**相同就直接 return，一个字节都不碰缓冲** → 静止时画面完全静止、零重传。
   - 写失败时**不要**更新 `lastText`（否则缓冲恢复后面板永远停在旧内容）→
     渲染里故意不 pcall，让异常抛到 `tick` 的 pcall 里统一处理。
2. **异常去重**：某一帧开始每帧抛同一个错时，旧写法把同样的消息每帧往 Scripting
   控制台灌一次 —— 看着也像在闪。判据取 **「错误消息变了才再报」**。
   - ⚠️ **不能用「成功后复位」**：渲染每 4 帧才跑一次，中间那些「成功但没渲染」的帧
     会把状态复位 → 下一个失败帧又报一次 → 照样刷屏。这个坑自测直接抓到了。

**验证**：自测加第 10 节（114 → **126 项**），用假 buffer 计数 `clear` 次数 + 假
`emu.read8/16/32` 注入故障，断言「不变不重画」「同一异常只报一次」「缓冲恢复后能重画」。

**可复用**：mGBA 的 `TextBuffer` 是**拉模式**（写才重传），所以「什么都不做」才是
最稳的渲染策略；任何「定时无条件重画」的面板都会闪。

## 经济报告：把「重量」纳入模型

**用户要求**：规划经济时「**要考虑重量**」。

### 公式与判据（先定死的部分）

GBA 火纹（FE6/7/8 同）的攻速与追击：

```
攻速 = 速度 − max(0, 武器重量 − 体格)     // 只有超出的部分才扣
追击 ⟺ 我方攻速 − 敌方攻速 ≥ 4            // DOUBLE_THRESHOLD = 4
追击 = 直接多打一次（伤害 ×2），不是 +50%
体格（con）没有成长 —— FE8 里不随等级涨
```

⚠️ 反直觉点：**体格大 ≠ 带得动**。上限是 `体格 + 速度 − 敌攻速 − 4`，
所以 Armour（con 14 / spd 11）的重量上限只有 11 —— 比 Thief（con 6 / spd 23 → 15）还低。

### ⚠️ 敌方攻速读不到（本轮最大的坑）

  TUTORIAL / TRAP×2 / PLAYER_UNIT×2 / FREEMAP_PLAYER_UNIT×3 / FREEMAP_ENEMY_UNIT×3 /

- 敌人不是靠条件表挂的，走的是**地图变更数据**（`MapChange`），本 CLI 没解析。

→ 只能取常数 `ENEMY_AS = 10`，并在报告里给 6 / 10 / 14 三档敏感性。**这是整份报告最粗的假设**，

## 把攻速/追击公式从「公知」升级成「ROM 代码级核实」

上一节里 `攻速 = 速度 − max(0, 重量 − 体格)` 和「阈值 4」都是**按公知公式写进报告的**。

### 关键发现：`patch2/` 里的 `#ENGINE` 补丁是**地址预言机**

先找的是「FEBuilderGBA 里有没有算攻速的代码」，翻了一圈没有（它是编辑器）。
但 `ls FEBuilderGBA/bin/Debug/config/patch2/FE8U/SYSTEM/` 里有两个补丁名字直接点题：

| 补丁文件 | 关键字段 |
|---|---|
| `PATCH_Eliminate attack speed penalty.txt` | `DETERMINATION_ADDRESS=0x02AB92`；`OFF:0x02AB92=0x40 0x1A`；`FIX=0xC0 0x46` |
| `PATCH_Required pursuit attack speed difference.txt` | `ADDRESS=0x02AFBC 0x2AFCE` |

`OFF:` 里的 `40 1A` 就是 **改前的原始字节**。拿它去 ROM 的 `0x02AB92` 一对 —— 一模一样
→ 「这条指令还在原地」。**这比翻符号表快得多**，以后找任何机制的地址都该先看 `patch2/`。
（写进 MEMORY.md 的第 ④ 条教训。）

### 反汇编结果

`BattleLoadAS @ 0x0802AB74`（符号表 `{U}` 版；J 版 `0x0802AAE4`）：

```
0802AB82  lsrs   r1, r7, #2      ; 物品字段 >> 2 = 武器重量
0802AB84  ldrsb  r0, [r4, r0]    ; 体格
0802AB86  subs   r1, r1, r0      ; 重量 - 体格
0802AB88  cmp    r1, #0
0802AB8A  bge    #0x802ab8e
0802AB8C  movs   r1, #0          ; ← max(0, ...) 的钳位
0802AB8E  movs   r0, #0x16
0802AB90  ldrsb  r0, [r4, r0]    ; 速度（单位 +0x16 有符号字节）
0802AB92  subs   r0, r0, r1      ; ★ 速度 - 惩罚   ← 补丁标的地址
0802AB94  adds   r1, r4, #0
0802AB96  adds   r1, #0x5e
0802AB98  strh   r0, [r1]        ; 存到 战斗单位 +0x5E = 攻速
0802AB9A..AB A2  钳到 0
```

`BattleCheckDoubling @ 0x0802AF90`（J 版 `0x0802AF00`）：

```
0802AFAE  ldrsh  r3, [r1, r5]    ; A 方攻速 (+0x5E)
0802AFB2  ldrsh  r2, [r2, r1]    ; B 方攻速 (+0x5E)
0802AFB4  subs   r1, r3, r2      ; AS_A - AS_B
0802AFBC  cmp    r1, #3          ; ★ 补丁 ADDRESS 之一
0802AFBE  ble    #0x802b010      ; ≤3 → 不追击
0802AFCC  subs   r0, r2, r3      ; 镜像分支
0802AFCE  cmp    r0, #3          ; ★ 补丁 ADDRESS 之二
0802AFD0  ble    #0x802b010
```

**结论**：`攻速 = 速度 − max(0, 重量 − 体格)`、`追击 ⟺ |攻速差| ≥ 4`（**双向**），
且攻速存在**战斗单位 `+0x5E`（u16）**。补丁标的 3 个地址与反汇编**逐个吻合**
→ 这个 hack 没动过这段代码，原版公式原样成立。

## 追问「§8 局限这三条什么意思」→ 顺手核实特效倍率

用户圈出报告 §8 的前三条局限问「什么意思」。解释过程中发现第三条
（「特效系实战价值远高于表上排名」）只说了结论、没给倍率，于是核实了一次：

`BattleLoadAttack @ 0x0802AABC`（U 版）里，算完基础攻击力后：

```
0802AAE8  bl       #0x8016c88      ; IsSlayerApplied
0802AAF0  cmp      r0, #1
0802AAF2  bne      #0x802ab00      ; 不成立就跳过
0802AAF6  ldrsh    r1, [r4, r0]    ; r1 = 武器威力（攻击力存战斗单位 +0x5A）
0802AAF8  lsls     r0, r1, #1      ; ×2
0802AAFA  adds     r0, r0, r1      ; ×2 + ×1 = ×3   ★
```

**特效成立 → 武器威力 ×3**（是「武器威力 ×3」，不是「伤害 ×3」）。
相关：`IsWeaponEffective @0x08016BEC` / `IsSlayerApplied @0x08016C88` /
`GetItemEffectivenessPtr @0x080176D0` / `gSlayerEffectivenessTable @0x088ADF39`（**数据段**）。

**一个反直觉的算法结论**：把 Ridersbane 的 3 倍算进去，它的含追击期望/金 从 0.15 涨到 0.45，
**仍然低于 Steel Lance 的 0.86**。所以「特效系被低估」这个说法不够准确 —— 真正的区别是
**§3 衡量「效率」（每金换多少伤害），不衡量「够不够」（能不能破防）**。
敌人防御一高，便宜武器是 0 伤害，`期望/金` 这个比值本身就失效了。

→ 结论写进 AGENTS.md §3.18.5 + MEMORY.md：**§3 只能决定「日常批量采购」，
特效系/银系买什么必须看具体地图。**

回答这三条时做了一张可视化（「追击判定需要双方攻速，你的可算、敌方的读不到」+ 6/10/14 敏感性条），

### ③ ⚠️ 然后我写错了一次，并自己抓回来

第一遍反汇编 `GetAutoleveledStat @ 0x0802B9C4`，看到 `bl 0x08000C80`，**凭形状当成除法 helper**，
于是写下「闭式算术、一个随机数都不烧，所以敌方属性是确定的」，还进了报告和 AGENTS.md。

查 `asmmap` 一看：**`0x08000C80` = `NextRN_N`**。而且 `GetStatIncrease @ 0x0802B9A0` 里
`bl 0x08000CA0` = **`Roll1RN`**。两个都是随机数。

```
GetAutoleveledStat:
  muls r4, r1, r4      ; v = 等级 × 成长
  asrs r0, r0, #3      ; v / 8
  bl   0x08000C80      ; ★ NextRN_N(v/8)  → ±v/16 抖动
  asrs r0, r0, #4      ; v / 16
  subs r0, r1, r0
  adds r0, r4, r0      ; v + RN − v/16
  bl   0x0802B9A0      ; GetStatIncrease(...)

GetStatIncrease:
  每满 100 → 保底 +1（循环）
  bl   0x08000CA0      ; ★ Roll1RN(...) 决定余数进不进位
```

**正确结论**：敌方属性 = `成长 × 等级 / 100`（基准，确定）**+ 很小的随机成分（±1 点）**。
真要做的话，输出应该是「基准值 ± 1」的区间，不是单一确定值。

**教训（已写进 MEMORY.md 第 ③ 条）**：反汇编里看到 `bl <addr>` **必须去 `asmmap` 查那个地址**，
不能凭形状猜。`0x08000C0C–0x08000CC0` 这一小段就是 RNG 函数族
（`LoadRNState`/`StoreRNState`/`NextRN_100`/`NextRN_N`/`Roll1RN`/`Roll2RN`）。
「这段算术确定」和「这段算术带随机」是相反的两个结论，猜错等于整份报告的性质变了。

## 敌人属性投影：把 `ENEMY_AS = 10` 换成逐阶段真实分布

用户批准了上一轮结尾的提议（「接上之后就能把 `ENEMY_AS = 10` 换成逐章敌人攻速分布，
重做 §3.0 的敏感性表」）。这一轮做完了，**没有硬接** —— 先花了大半轮把公式核实到指令级。

### ① 公式与四项来源

```
敌攻速 = 职业基础速度 + 角色表增量 + 自动升级 − max(0, 武器重量 − 体格)
```
分别来自：职业表 `+0x0E`/`+0x11`；角色表 `+12..19`（**有符号**）；
`AutolevelUnit @0x08018120`（用**职业**的 `enemyGrowths @+0x1B`）；道具表 `+23`。

### ② 决定性发现：`+3` bit 0 是自动升级的总开关

`0x08017C10`（`Event2C_LoadUnits` 一路走下来的第一件事）：

```
08017C10  ldrb r1, [r6, #3]     ; 记录[+3]
08017C14  ands r0, r1, #1       ; GROW
08017C18  beq  #0x8017cb8       ; == 0 → 完全跳过自动升级
```

**在阵营判断之前**。编辑器里这一位叫「成長率: 成長させない / クラス依存」。
DoF **303/2805 = 11%** 的敌人记录是 0。**我原来的模型漏了这一层。**

### ③ `unit[+0]` = pCharacter、`unit[+4]` = pClass（顺序极易搞反）

证据链：
- `AutolevelRealistic @0x08018160`：`ldrsb r0,[r4,#8]`（等级）− `ldrb r1,[unit[0],#0xb]`
  → `count = 等级 − 角色表初始等级`。**角色表 `+0x0B` 就是等级。**
- `IncreaseUnitStatsByLevelCount @0x08017FC4`：`ldr r0,[r4,#4]; ldrb r0,[r0,#0x1b]`
  → 成长率取 `unit[4]->+0x1B`。**职业表 `+0x1B` 就是 `enemyGrowths`。**

所以 `unit[4]` 是**职业**，敌人用职业成长率 —— **原模型是对的**。
（顺带：`IncreaseUnitStatsByLevelCount` 的第二个参数那个 id **函数里根本没读**。）

### ④ 两条路径的分派（`0x08017C36`）

`(角色.abilityFlags[1] | 职业.abilityFlags[1]) & 0x80` 置位 → `AutolevelRealistic`；
否则角色 id > 0x40 → `AutolevelUnit`；否则也是 `AutolevelRealistic`。
实测 **2458 / 44 / 303（无）**。

`AutolevelRealistic` 是「用角色自己的成长率逐级模拟 `CheckForLevelUp @0x0802BA28`」，
所以均值 = `角色成长 × count / 100`，但分布是二项分布。

### ⑤ 转职那一轮的掩码是 `0x100`（我原先记错了）

`0x0801812E`: `movs r1,#0x80; lsls r1,r1,#1` = `0x100`
→ `(角色.abilityFlags[1] | 职业.abilityFlags[1]) & 0x01` = 特性2 bit0「上級クラス(武器S)」。
**是 `& 0x01` 而且角色与职业要 OR 进来**；我记忆里写的 `cls.abilityFlags[1] & 0x02` 是错的。
加成值 `GetCurrentPromotedLevelBonus @0x08037B44`：`gChapterData[0x14] & 0x40` → **19 / 9**。

### ⑥ 三个「看起来像 bug 其实是对的」

1. **负攻速**：`BattleLoadAS` 从有符号字节里减惩罚，引擎不钳零。74/2805 条为负 ——
   Gorgon Egg（速 0 拿 w10 的书 → −4）、Artillerist（速 0 拿 Ballista w20 → −11）、
   Arch Mogall（体格 5 拿 w20 → −8.8）、Warlock（体格 10 拿 w20）。
2. **map31 整章中位 −2**：那章 45 条记录里 **24 个是 Gorgon Egg**。它是 `@001F` 遭遇图，
   不在任何路线阶段里，所以不影响报告。
3. **2805 vs 2723**：`collectPlacementSites` 按**章内**去重（2805），普查脚本再按**全 ROM** 去重（2723）。
   Lagdou Ruins 10（map 55）与 C15（map 36）共享 5 个配置块 —— 两个数都对。

### ⑦ 一个我自己踩的坑（值得记）

`economy-plan.ts` **自己会写文件**，我又用 `node scripts/economy-plan.ts > out/xxx.md` 重定向到
