### Verified FE7 ROM facts (extracted from the C# source)

- **Version detection**: 6 ASCII bytes at file offset `0xAC`. `AE7E01`=FE7U, `AE7J01`=FE7J,
  `AFEJ01`=FE6J, `BE8E01`=FE8U, `BE8J01`=FE8J. FE7/FE8 ROMs must be ≥16MB, FE6 ≥8MB.
- **CRITICAL**: `RomInfo.*_pointer` fields are the file offset of a **pointer slot**, NOT the
  table itself. Table offset = `p32(slot)`. Proof: `PatchForm.cs:9372 ReplacePointerSub()` reads
  `u32(RomInfo.item_pointer)` as a raw GBA pointer; `InputFormRef.cs:5792 Init()` does
  `BaseAddress = p32(BasePointer)`. Fields ending in `_address` are direct offsets (no deref).
- `p32(a)` = read u32, and if in `[0x08000000, 0x0A000000)` subtract `0x08000000`.
  `p32p(a)` = `p32(p32(a))`.
- **Field offsets live in WinForms control names**: `<B|W|D|P><byteOffset>`
  (B=1, W=2, D=4, P=4 bytes). Defined at `InputFormRef.cs:5037 GetDataSize()`.
  Label `Text` next to each control is the field name (Japanese).
- FE7U pointers: unit `0x9A274`, class `0x178F0`, support_unit `0xBDCE78`,
  support_talk `0x78A94`, support_attribute `0x26998`, mask `0x6BC`,
  mask_point_base `0x6B8`, text `0x12CB8`, text_recover `0xB808AC`, is_multibyte=false.
- FE7J pointers: unit `0x9AC50`, class `0x17CE0`, support_unit `0xC4C184`,
  support_talk `0x79264`, support_attribute `0x26E24`, mask `0x6E0`,
  mask_point_base `0x6DC`, text `0x13370`, text_recover `0xBBB370`, is_multibyte=true.
- **Unit record = 52 bytes**, IDs are **1-based** (ID n at `table + (n-1)*52`):
  +0 u16 name text id, +2 u16 desc, +4 u8 id, +5 u8 base class, +6 u16 map face, +8 u8 portrait,
  +9 attribute, +10 sort, +11 level, +12..18 stats (HP/Str/Skl/Spd/Def/Res/Lck), +19 con,
  +20..27 weapon levels (sword/lance/axe/bow/staff/anima/light/dark), +28..34 growths,
  +35/+36 palettes, +37/+38 custom anim, +39 ?, +40..43 ability flags,
  **+44 p32 support data pointer**, +48 talk group, +49..51 ?.
- **Class record = 84 bytes**, IDs are **0-based**: +0 u16 name, +2 u16 desc, +4 u8 id,
  +5 u8 promote-to class, +6 wait icon, +7 move speed, +8 u16 generic face, +10 sort,
  +11..17 bases (HP/Str/Skl/Spd/Def/Res/Con), +18 **move range**, +19..25 caps,
  +26 exp bonus, +27..33 enemy growths, +34..39 promotion bonuses, +40..43 ability flags,
  +44..51 weapon levels, +52/+56/+60/+64 move-cost & battle-anim pointers,
  +68/+72/+76 terrain avoid/def/res pointers, +80 u32 ?.
- **Support record = 24 bytes** (indexed ONLY via unit `+44`, not by ID order, no fixed count):
  +0..6 seven partner unit IDs, +7..13 their initial support values, +14..20 their growth values,
  +21 partner count (max 7), +22..23 padding. Stored **bidirectionally** (A→B and B→A are
  separate records) — dedupe when building a support graph. Unit IDs > `0x45` are enemies and
  have no growth value.
- **Support talk record = 20 bytes**: +0 u8 unit1, +1 u8 unit2, +2 u16 pad,
  +4/+8/+12 u32 text IDs for C/B/A conversations, +16..19 unknown.
- **Support attribute record = 8 bytes** (per support rank C/B/A).
- **Text is Huffman-compressed**: text ID → `text_pointer` table → per-string pointer → bit tree
  at `mask_pointer`/`mask_point_base_pointer`. Algorithm at `FETextDecode.cs:327 huffman_decode()`
  plus `append_string()` and `listbyte_to_string()`. Escape codes render as `@XXXX`.
  Advise porting those three functions line-by-line rather than reimplementing from spec.
- Localized/Chinese ROMs may carry anti-huffman or UTF-8 text patches
  (`PatchUtil.SearchPriorityCode()`); decoding names may fail — verify by decoding unit 1's name.

### 本轮修掉的两个真 bug

1. **文本只实现了 Huffman，漏了「未压缩」分支。**
   症状：255 个角色里 128 个名字是空串，但这些记录的**其他字段全正常** ——
   差点误判成「文本表有洞」。
   根因：文本表条目值可能是 `0x88000000..0x8A000000` 的 un-huffman 补丁指针
   （= 真实指针 `+0x80000000`），指向**明文存储**的字符串，要用变长字节游走解码，
   不能用 Huffman 位流解码器。
   修复后 249/255 可解（剩下 6 个 nameTextId=0，是真的没名字）。
   实现：`UnHffmanPatchDecodeLow` 逐行移植自 `FETextDecode.cs`。

2. **职业表按 `maxCount` 读满，把表尾的别种数据当成职业记录。**
   症状：职业 ID 大量重复（255 出现 18 次），`classNames` 映射被垃圾记录覆盖，
   某个职业的晋升目标显示成 `"--"`。
   根因：职业表只有 128 条（id 0..127），之后是链接器塞的其他数据。
   `ClassForm.Init()` 的读入判定是「index 0 恒保留；此后遇到 `u8(addr+4)==0` 即停」。
   顺带确认：**角色表用固定条数**（`i < unit_maxcount`），两张表规则不同。

## 解耦：`cli/data/` vendored 副本（用户：「data.ts 的写法是耦合了 FEBuilderGBA 吧？直接把数据复制过来」）

**CLI 和 C# 仓库耦合**，单独 clone `cli/` 跑不起来。用户要求把数据直接复制过来。

1. 复制**最小子集**到 `cli/data/`：3 前缀（`unitclass_checkbox_` / `event_` / `eventcond_`）

2. 重写 `defaultConfigSearchPaths()`：只返回 `[$FEBUILDERGBA_CONFIG, cli/data]`，
   删掉所有 `FEBuilderGBA/...` 路径。模块 docstring 记录来源与刷新方式。
3. 更新 `load.ts` 的 `configDir` 注释（不再说「FEBuilderGBA 的目录」）。
4. `cli/data/` 未被 `.gitignore`（只忽略了 `cli/node_modules/` 和 `cli/out/`），会进版本控制。

## 反汇编 ROM 自己的代码 —— 支援系统的全部算术（第三次「想当然」的纠正）

**触发**：用户问「支援数值和地形名字为什么不可得」。地形名字那半边上一轮已修；
这一轮把「支援数值」这半边彻底做完，并发现**第三个错误结论**。

### 最大的技术收获：ROM 自带符号表 + 反汇编

**`FEBuilderGBA/bin/Debug/config/data/asmmap_FE8.txt`（还有 `.en` / `.zh`）是原版 FE8U 的
「函数名 → 地址」映射**（tab 分隔：`地址 <TAB> 名字 <TAB> 说明`，`{U}`=美版 `{J}`=日版）。
**等于给原版 ROM 附了一份带注释的反汇编清单。** hack 保留了原版代码布局，符号表直接可用。

反汇编器：本机 `objdump` 是 LLVM 21，**不支持裸二进制**（`-b binary` 是 GNU 专属）。
用 Python `capstone`（装在 `~/.workbuddy-ai/binaries/python/envs/default`）。
脚本已存进 skill：`~/.workbuddy-ai/skills/febuildergba-rom-extraction/scripts/disasm.py`。

`grep -i support asmmap_FE8.txt` 直接给出整条函数链，反汇编后拿到：

| 结论 | 反汇编证据 |
|---|---|
| 表步长 8、`u8(a)==相性` 匹配、`u8(a)==0` 终止 | `adds r2,#8` / `cmp r1,r3` / `cmp r1,#0` |
| **`support_attribute_pointer` 槽就是函数字面量池里的字** | `ldr r2,[pc,#0]` 落在 `0x28534` |
| 加成 = `存值 × level`，level ∈ {0,1,2,3} | `ldrb r1,[r0,#1]` + `muls r1,r5,r1` |
| **六项各 `>>1`，只除一次** | 函数末尾 6 组 `ldrb`/`lsrs #1`/`strb` |
| 门槛 `>0x50→C, >0xA0→B, >0xF0→A` | `GetSupportLevelBySupportIndex` 三个 `cmp` |
| 距离判据是曼哈顿 `|dx|+|dy|` | `subs`+abs+`adds r0,r1,r0`+`cmp r0,#3` |
| 偏移 7 从不被读（只是填充） | `StoreAdded` 只写 `#1`–`#6` |

第二意见：FE8 反编译 `FireEmblemUniverse/fireemblem8u`（**注意 FE8 把 support 叫 `reliance`**，
`grep support` 在 include/ 搜不到，要找 `bmreliance.h`）。头文件给出字段名与常量：
`SUPPORT_EXP_C/B/A = 81/161/241`、`MAX_SIMULTANEOUS_SUPPORT_COUNT = 5`、
`SUPPORT_BONUSES_MAX_DISTANCE = 3`、`struct SupportBonuses` 的六字段顺序、
`struct SupportData` 计数在 `+0x15`（22 字节，但本 ROM 按 0x18 对齐）。

### 第三个错误结论：相性表「和公版对不上」

我上一轮写下：「本 ROM 每行都给 `atk+1` + `critAvoid+5`，Dark 与 Light 完全相同，
公版每行只给四项且各行互不相同 → 表被改过或指错了」。**错的。**

真相：**表里存的是半点值**，游戏在 `GetUnitSupportBonuses` 末尾对六字段各做一次 `>>1`。

```
存 1 → C:0 B:1 A:1     存 5 → C:2 B:5 A:7
```

展开后 7 行**精确落在公版 GBA FE 相性表上**，**`Dark == Light` 也是公版行为**。
表就是未改动的公版 FE8U 表。

**教训（比前两次更隐蔽）**：数据读对了，但**误解了量纲**，于是把「值不符合预期」
当成「ROM 数据有问题」。→ **「值看起来像脏数据」时，先怀疑自己漏了一层变换
（×2 / ÷2 / 有符号 / 单位 / 累计 vs 增量），别先怀疑 ROM。**
这时正确动作是**反汇编 ROM 自己的代码** —— 它在 5 分钟内就给出了 `lsrs #1`。

完整公式：`floor( Σ_相邻伙伴 ( 行[我方相性]×L + 行[对方相性]×L ) / 2 )`，L = 0/1/2/3。
三个反直觉点：① **双方相性都算**；② `>>1` 只做一次、作用在总和上；
③ **A 级 = 原始值×3 再取整**（`5×3>>1=7`），不是 `C 级取整后×3`（`2×3=6`）。

### 门槛与「能升级的点数」差 1

点数**会封顶**，必须真的看支援对话才进下一级（`UnitGainSupportExp` + `CanUnitSupportNow`）：

```
等级「无」→ 最多涨到 80 → 对话可用 → 对话后 81 → C
等级 C    → 最多涨到 160 → 对话可用 → 对话后 161 → B
等级 B    → 最多涨到 240 → 对话可用 → 对话后 241 → A
```

- **80/160/240 = 解锁对话的点数**（`SUPPORT_CONVERSATION_CAPS`）
- **81/161/241 = 对话之后持有的点数**（`SUPPORT_RANK_THRESHOLDS`，也是参考程序 EXPLAIN 里写的）
- 所以到 C 的回合数 = `ceil((80 − 初始值) / 成长值)`，**不是 81**。上一轮按 81 算是错的。

另外由代码核实：加成生效 **3 格**、攒点数 **1 格**（一人背另一人也算）、
**单人可持有支援等级总数上限 5**（A=3,B=2,C=1 求和）、每对每章只能升 1 级。
