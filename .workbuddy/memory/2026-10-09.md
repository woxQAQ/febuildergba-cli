### 输出消融（第二轮，重要经验）

用户指出"全量章节表没意义"+"大量无用数据"，实测确实是输出模型的 bloated：

**Vision Quest 上 `chapters` 命令原本 535KB**，是 `storypath`(27KB) 的 20 倍。
消融后 177KB（-67%），`storypath` 24KB（-10%）。三处根因：

1. **`placements` 912 条 vs `joinOrder` 62 条**。placement block 是每部署槽一条，
   hack 复用单位 id 当通用模板导致膨胀。改成 `roster`（按角色去重，含多等级的
   `levels[]`），每图从 4083B 降到 729B。
   **注意：579 条 classOverridden 全是真实可操作单位**（大量被改成 Paladin/Brawler），
   这个信息有队伍价值，不能直接丢，所以保留在 `roster` 里而不是简单过滤掉
2. **`recruitSites` 284 条里只有 62 个可操作角色**，其余 142 个是敌人/通用模板。
   改名 `midChapterRecruits` 并按 supportIds 过滤
3. **填充行默认输出**：地图表 79 行只有 60 张真图。加 `isPaddedRow` 标记，
   默认过滤，`--all` 可见。复用 `storyPath.isRealMap` 保证两命令判据一致

**方法论**：判断字段该留不留，要先统计数据（多少条、覆盖了什么、是否被消费方用到），
而不是凭字段名猜。我先查了 `joinOrder`/`placements` 的字段差集和实际条数才动手。

### 主流程：chain 41 张 / reachable 49 张，7 个外传强制插入

`map 0→1→…→11→12→13→14→15→16→41→42→17→18→19→59→43→20→61→21→…→27→28→…→35`

**章节号在这条链上重置四次**（map 0/12/18/21 都是 ch1），所以按章节号排序会造出
不存在的分幕 —— 这就是必须读 END_EVENT 的原因。

7 个外传关卡强制插在主线中间（一个 map 有多个前进目标）：
map 6→63、12→40、14→38、16→36、21→37、23→39、59→46。
**队伍配置含义：外传关强度要算进预算，不能当"有空再去"；但它们不在 chain 里，
要读 `reachable`。**

Dream of Five 上同一命令：chain 7 张 / reachable 33 张（含半步章节 6.5），正常。

实现要点：
- 跳转指令 `212A` MNCH / `222A` MNC2 / `232A` MNC3 / `2025` LOMA，全带 `{MAP}` 分类。
  **搜指令要搜 MNCH/MNC/LOMA**，不是"マップ"/"JUMP" —— FE8 命名与 FE6/FE7 不一致
- **必须走 `disassemble`**，不能手写字节扫描：指令表最长匹配优先，
  手写扫描在第一个变长操作数处就错位（症状：目标值全是 0）
- 参数符号名是单个字母（`sym: "X"`），不是 `"XXXX"`
- `EventScriptDef` 字段是 `description`/`category`，没有 `info`/`name`
- `{MAP}` 分类会误抓 FADI/FADU/STAL/TILECHANGE（操作数恰好落在 0-79），要按助记符白名单过滤
- **LOMA 是"切图"但也用于章节内传送**（map 29 有 5 个），不能当章节分支。
  路径追踪只认 MNCH/MNC2/MNC3
- **起点判定不能用"无入边"**：map 0 有来自 map 57（通关后图）的入边。
  正确判据是"章节号 1 且没有**真实有编号章节**指向它" —— 要先滤掉占位行和无编号图

### CLI 坐标与接口约定（踩过的坑）

- `RomBuffer.u8/u16/u32` 收的是**文件偏移**，不是 GBA 地址。`0x8B0890` 直接当文件偏移用
- `loadRom()` 返回 `LoadedRom`，RomBuffer 在 `.rom` 字段，`.chapters`/`.configDir` 平级。
  给 `disassemble` 传 `loaded` 会报 `rom.u8 is not a function`
- `fe-rom` CLI 用**绝对路径**跑 ROM 正常，相对路径会ENOENT
- `cli/src/commands/supports.ts:60` 有个**改动前就存在**的 tsc 错误（`byRank` 不在
  `SupportBonus` 上），不是新引入的

### 教训

连续四轮结论出错（route 语义、占位行分母、章节号每幕重置、声称无跳转指令），共同原因：

## 输出消融（第三轮）

四项改动（Vision Quest 实测）：

1. **`units` 默认裁到名单** 255 → 62 行，-281 KB。193 条敌人/通用模板行占 74%。
   `analyze.py` 本来就是配 `--playable-only` 跑的，默认输出从没被消费过。
   `chapters` 的 `joinOrder` 一直是这个默认，这次让 `units` 与之一致。
2. **`supports.byUnit[].partners` 只留 id+name**，-81.6 KB。`edges` 是每个无序对
   一行（159 条，`a<b`）并带全部数值；`partners` 是双向 318 条重复。
   反向数值不会丢：不一致时 `buildSupportGraph` 存进该边的 `mismatch`。
3. **`chapters.midChapterRecruits` 只留 `kind==="recruit"`（LOAD1）**，122 → 47 条。
   `412C/422C` 是 LOAD2/LOAD3，装的是已在队伍里的单位，不是招募，却占了这一块 82%。
4. **`chapters.forcedUnits` 去掉每图的 `everyMap` 重复**，159 → 39 条。
   `mapIndex=0xFF` 的记录原样出现在全部 60 张图上（159 条里 120 条是两条记录的副本），
   现在只在顶层 `forcedDeployment.everyMap` 出现一次。消费方要并集。
5. **`classes.impassableTerrains` 移到 `--all`**，-53.2 KB，无消费方且最可重建。

顺带修 bug：`supports.affinityBonuses[].byRank` 一直是 `b.byRank`（`SupportBonus` 上
不存在），JSON 会丢掉 `undefined`，所以注释承诺的 C/B/A 数值从来没输出过。
改 `rankedBonus(b)` 后是 +6.6 KB —— 这不是消融，别和上面数字混着算。

方法要点（本轮最重要的经验）：
- **"无用数据"多半是重复，不是冗余字段**。三个大头都是同一事实被写了 2~60 遍。
  判据落到"条目数 vs 去重后事实数"：318 vs 159、159 vs 39、122 vs 47。
- **默认输出和真实被消费的输出可能不是同一份**。只看命令实现看不出来，
  必须去读消费方（`analyze.py` 把 255 行打印成 "playable units: 62"）。
- 反例也要量：空数组（`goldEvents: []` 55/60）合计只有 1 KB，不值得引入可选键。

保真验证：`tsc` 干净；两个 ROM `validate` 52 项 0 错；18 项前后 JSON 对比全过；

`reports/vq/*.json` 与 `full-analysis.txt` 已重新生成，`analyze.py` 已同步并集写法。

## 输出模型去噪（第四轮）

判据纠正：上一轮做的是**去重**，用户指出要的是**去噪**（去掉对我们没用的）。
新判据：**输出只保留"这个 ROM 作为一款游戏的事实"；只服务于解析器自身的记录是噪音。**
三类：定位信息（地址/指针）、解码残留（原始字节、未解码字符串）、
解析器账目（逐条 dump、数字的来源分解、推断来源标记）。

最先纠正的一件事：**先确认命令清单完整**。上一轮把 `enemy-stats` 拼成 `enemyStats`，
错误被 `2>/dev/null` 吃掉，所以 1.25 MB 的 `enemy-stats`（比其余 11 个命令加起来还大）
整轮都没进过统计。

结果（VQ 默认输出）：**2108.1 KB → 1043.0 KB，-50.5%**（12 个命令）。
`enemy-stats` 1221.8 → 233.1 KB（-80.9%）；dream-of-five 抽查 -55.4%，比例一致。

四项大改：
1. **`enemy-stats.samples` 移到 `--all`**（-843.8 KB = 全部输出的 39%）。
   3246 行逐条投影；同一批数字已由 `overall`/`byRoutine`/`chapters[].summary`/
   `chapters[].classes[]` 表达；无消费方（`validate.ts` 读的是进程内对象不是 JSON）。
   即使 `--all` 也不再输出 `unitId`（通用模板行 id，不是角色）与 `grow`（`routine` 已表达）。
2. **地址/指针**（1093 处 / 27 KB）：`chapters` 每章 5 个指针 + `recordAddress` +
   `joinEvidence` + `midChapterRecruits[].address` + `mapSettings`/`forcedDeployment.table`
   的地址；`units.supportAddress`/`evidenceAddr`；`objects.address/event/shopList`；
   `shops.address`；`terrain.nameAddress`；`items/terrain` 的 `table.slot/address`。
   代码自己的注释就写着 "Raw table pointers, for auditing a decode"。
3. **解码残留**：`units.nameRaw`、`supports.affinityBonuses[].raw`、`terrain.raw`/`shape`。
4. **解析器账目**：`roles` 的 `mobilitySource`/`abilityFlags`/`classMobilitySummary`/
   `mobilityDisagreements`/`flagSource`；`items`/`terrain` 的 `idHex`；
   `objects.objectType`（`objectTypeName` 已是解码）；`supports.byUnit[].declaredCount`；
   `enemy-stats.chapters[].classes[].classBaseSpd`/`meanUnitSpdDelta`（答案的输入不是答案）。

**两个有意保留的例外**（别下轮又删）：
- `info` 的全部地址——它的职责就是报地址，删了没别处可查。
- `chapters[].itemsGiven[].address` / `goldEvents[].address`——**跨章去重键**，
  一个脚本被多张图引用，删了会把一笔 5000 金币算 17 次。

`terrain` 默认行数 65 → 62（3 行无名字、只有原始字节），`--all` 仍全给。

保真：`tsc` 干净；两 ROM `validate` 52 项 0 错；全命令冒烟 14/14 × 2；
diff 删除 4455 处 / 37 字段，**新增 0 字段**、非预期变更 0；
